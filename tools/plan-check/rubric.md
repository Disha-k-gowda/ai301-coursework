# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated diagnosis read against the reproduced evidence, including observed behavior, expected behavior, commands, and output. | Pass when the diagnosis identifies a cause that is supported by the reproduced evidence and does not contradict the observed behavior. Fail when the diagnosis is unsupported, contradicts the reproduction, or merely restates the symptom without identifying what is causing it. | required |
| scope-bounded | The plan's scope statement, files to change, and stated non-goals read together. | Pass when the proposed change is limited to the reproduced problem and the listed files or components have a direct role in that fix. Fail when the plan includes unrelated cleanup, refactoring, features, or changes whose connection to the reproduced problem is not established. | required |
| cause-targeted | The proposed approach read against the plan's diagnosis and reproduced evidence. | Pass when the proposed change directly addresses the diagnosed cause of the reproduced behavior. Fail when it only hides, bypasses, or patches the visible symptom while leaving the diagnosed cause unchanged. | required |
| executable | The files to touch and implementation approach read with the repo facts and conventions supplied in the package. | Pass when the plan identifies the relevant code, documentation, configuration, tests, or bounded component to change and describes enough implementation behavior that another contributor could begin the change without first having to determine the basic implementation strategy. Exact functions or lines may remain to be located during implementation when the component, intended behavior, and starting point are already concrete. Fail when the main change location, affected component, or implementation behavior still has to be discovered before work can start. | required |
| test-observable | The test plan read against the reproduced evidence's original steps, inputs, expected behavior, and observed failure. | Pass when the test plan re-runs the relevant reproduction path or an equivalent real-code check and states an observable post-fix result that distinguishes the fixed behavior from the reproduced failure. Fail when it only says to run tests, inspect the code, or confirm the fix without specifying an observable result tied to the reproduced behavior. | required |
| unknowns-honest | The plan's risks, assumptions, and unknowns read against gaps or uncertainty visible in the reproduction evidence and proposed approach. | Pass when any material uncertainty is either identified as an unknown/risk or resolved by evidence already present in the package. A plan does not need to invent an unknown when the available evidence reveals no unresolved material assumption. Fail when the plan presents an unresolved material assumption as established fact and that assumption could change the implementation or test strategy. | required |
| thread-conventions | The draft plan comment read against the issue thread highlights and the repo-facts or stated repository conventions in the package. | Pass when the comment is consistent with relevant maintainer requests, issue constraints, and repository conventions, and does not claim work or scope that conflicts with them. Fail when it ignores or contradicts a relevant thread requirement or stated repository convention. | required |

## Verdict rule

Accept only when every required check passes. Any failed or unclear required check makes the verdict reject. An unclear grade means the available package does not contain enough evidence to establish that the pass condition is met, so it counts as a failure. Preferred checks, if added later, may provide feedback but never change the final verdict.
